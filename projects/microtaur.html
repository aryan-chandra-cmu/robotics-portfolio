01 / Robot-learning problem

Learn locomotion, then make it executable on a small real robot

Microtaur is a custom eight-actuator, five-bar-linkage quadruped. A gait learned with ideal simulator state and idealized motor timing cannot simply be copied onto a device whose IMU, Dynamixel servos, and embedded compute have finite update rates and noisy feedback. My work spans both sides of that gap: PPO gait learning and distillation in simulation, and onboard closed-loop policy execution with real servo interfaces.

02 / System design

Two control pipelines, one deployment objective

A · Learn and distill a gait in simulation

MuJoCo / MJLab→PPO teacher→Teacher rollouts→Supervised student→Closed-loop evaluation
  • Teacher: 123-dimensional simulation input, network 123 → 512 → 256 → 128 → 8; optimized for velocity tracking, upright posture, and a light diagonal-contact preference rather than a fixed foot trajectory.
  • Student: 35 → 64 → 64 → 8, trained to reproduce teacher joint actions with a Huber loss and observation normalization.
  • Robot-ready 35D input: projected gravity (3), base angular velocity (3), eight relative joint positions, eight joint velocities, previous eight actions, velocity command (3), and gait phase encoded as sin/cos (2).
  • Closed-loop test: the student was evaluated while controlling its own simulated state, not just scoring prediction error on teacher snapshots.

B · Execute the learned controller on hardware

IMU + Dynamixel feedback→Observation normalization→Linux policy inference→Asynchronous action buffer→STM32 → 8 servos

The later physical implementation used an Arduino UNO Q: Linux performs policy inference; the microcontroller maintains the sensor/actuator loop, with state/action buffers, stale-feedback safeguards, and position targets for eight Dynamixel servos. The earlier ESP32-S3 research target and the later UNO Q implementation were different deployment paths; the 6,984-parameter student was evaluated in simulation, not presented as a completed ESP32-S3 deployment.

03 / Quantitative experiment

33× smaller policy; behavior preserved in simulation

0.187 m/sMean student speed

In the reported student evaluation, the controller ran for 20,000 steps across 256 parallel simulated environments without resets. Its mean forward velocity was 0.187 m/s against an average command of 0.210 m/s; the reported tracking error was 0.041 and absolute yaw rate 0.070. The student used roughly 3.1% of the teacher parameters while retaining similar gait behavior.

These are simulation-evaluation results for the distilled student, not physical-hardware speed or robustness measurements. The presentation identified ESP32-S3 deployment as future work. The real-hardware UNO Q controller represents a separate, later integration milestone.

04 / Integration engineering

The details that determined hardware behavior

01 /
Model the actual mechanism

Check five-bar leg geometry, action limits, contacts, joint conventions, motor response and commanded velocities.

02 /
Match real sensing

Construct observations consistently from projected gravity, angular rates, measured/estimated joint states, previous action and phase.

03 /
Synchronize compute and actuation

Separate variable-latency neural-network inference from the time-critical motor interface, buffer the latest valid action, and handle stale measurements.

04 /
Characterize physical servos

Evaluate Dynamixel tracking, PD gains, voltage limits, communication reliability, and load-dependent lag rather than assuming ideal position servos.

05 /
Close the sim-to-real loop

Compare visible behavior, motor tracking, simulation rollouts and hardware test recordings; adjust model assumptions and control cadence.

I encountered the practical limits of real-time loops when command frequency changed: some policies that looked acceptable in simulation became shuffly or unstable on the robot. This made actuator characterization, fresh observations and reproducible testing as important as reward tuning.

01 / Embodied autonomy

Translate human intent into constrained motion using a real camera and motors

A language model can identify an object in an image, but commanding a moving robot requires a very different interface: observations arrive slowly, actions must expire safely, and instructions such as “go to the person” need a bounded physical interpretation. I prototyped a phone-camera mobile robot with a local vision-language reasoning component and a separate deterministic ESP32 motor controller.

02 / System architecture

Phone senses and speaks; PC reasons; ESP32 executes

Poco smartphone camera + speech→Wi-Fi frame / instruction→Ollama Qwen2.5-VL 7B→Validated JSON action→ESP32-S3 motor + IMU
01 /
Collect multimodal state

Phone serves camera frames, spoken instructions (via speech-to-text), and a minimal interface for the robot’s state and responses.

02 /
Ground the request

A locally hosted Qwen2.5-VL 7B model on a PC interprets the scene and target with a structured output schema.

03 /
Validate action commands

Check the generated JSON, map actions to a controlled set and restrict movement duration/speed instead of executing arbitrary model text.

04 /
Control the vehicle

ESP32-S3 receives commands over Wi-Fi, drives motors, uses MPU6050 heading/yaw feedback, and applies motor stop/timeout logic.

05 /
Close the loop

After executing a bounded action, take another observation so the next decision uses updated physical state.

03 / What was implemented

Concrete components, tests, and integration limits

  • Local visual grounding: Qwen2.5-VL 7B was exercised on phone-camera inputs and successfully identified a person and earphones, estimated relative target positioning, and returned parsed JSON.
  • Expressive phone interface: project exploration included a “hey robot” wake-phrase interface, phone speech-to-text, spoken output and an expressive display.
  • Embedded control: ESP32 HTTP/JSON interface exposed bounded move_forward, move_backward, turn_left, turn_right and stop commands, with timeouts and telemetry.
  • Heading feedback: MPU6050-based yaw estimate and heading-hold / relative-turn control were designed to reduce wheel-motor drift.
  • Known failure: an early “stop when close” decision could trigger with a target still off-center; this motivated explicit target alignment and visual-servo stages rather than a single unstructured VLM response.

Prototype scope: verified component-level visual grounding and motor-controller testing support the perception → reasoning → bounded action architecture. Sustained autonomous person-following and object interaction remain future system-level evaluation targets.

04 / Key engineering choices

Why deterministic low-level control matters with VLMs

Model output

Typed, inspectable actions

LLM/VLM messages are validated against a small motion vocabulary before execution.

Physical safety

Timeouts and bounded PWM

Motor actuation expires if fresh, valid commands do not arrive.

Feedback loop

Separate reasoning/control rates

Camera/model inference runs slower than motor timing; yaw control and stopping stay on-device.

Failure analysis

Alignment before approach

Prevent premature “reached target” behavior when visual offset and physical proximity disagree.

This project is an exploration of an important embodied-AI boundary: semantic understanding is not a motor controller. It demonstrates how to couple a general-purpose VLM to a constrained action API while preserving debuggability and safety.

05 / Next engineering milestones

A clear roadmap, not inflated claims

  • Add repeatable task scripts for target acquisition, alignment, approach and stop with time/distance logging.
  • Collect labeled success/failure trials under changes in lighting and target position.
  • Use visual-servo feedback to correct off-center approaches and quantify latency.
  • Compare local VLM decisions against a deterministic perception/controller baseline.
